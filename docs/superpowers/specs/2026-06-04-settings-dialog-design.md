# Settings Dialog — Design

**Date:** 2026-06-04
**Status:** Approved (pending user review of this spec)
**Author:** Brainstorming session

## Purpose

Add a basic placeholder settings dialog to the Flutter boilerplate so that a user
can open it from the home screen. The dialog acts as a launcher for the
existing theme and language controls, and as a host for an About screen that
shows app metadata and device info. The dialog is intentionally a placeholder
surface — its rows are wired to live state, but no new persistence, accounts,
or notification preferences are introduced.

## Goals

1. Provide a single, discoverable entry point for app-level settings from the
   home screen.
2. Reuse the existing `ThemeStore` and `LanguageStore` so theme and language
   rows reflect and mutate live state.
3. Add an About dialog that pulls app version and device info at runtime.
4. Match the existing layered architecture (presentation / domain / data) and
   MobX conventions used by `home/` and `post/`.
5. Localize all new user-facing strings across `en`, `es`, `da`.

## Non-Goals (YAGNI)

- Account / profile management.
- Notification preferences.
- Logout from inside the dialog (the existing app-bar icon remains the path).
- Persistence of any new settings.
- Deep linking to the settings dialog.
- Unit testing the `SettingsStore` (its only behavior is a thin wrapper over
  two plugins; mocking the platform channels is out of scope for a placeholder).

## Architecture

A new `settings` feature is added under `lib/presentation/`, mirroring the
shape of `home/` and `post/`. No domain or data layer is added; the dialog
reads existing stores from `getIt` and the About dialog calls platform plugins
directly from a presentation-layer store.

```
lib/presentation/settings/
  settings_dialog.dart       // Main placeholder dialog (StatelessWidget)
  about_dialog.dart          // Secondary dialog with app + device info
  store/
    settings_store.dart      // MobX store: loads About info
    settings_store.g.dart    // generated by build_runner
```

### New dependencies (added to `pubspec.yaml` runtime dependencies)

- `package_info_plus: ^8.0.0` — read app name, version, build number.
- `device_info_plus: ^10.0.0` — read device model, OS version, manufacturer.

Versions will be resolved by `flutter pub get` at implementation time; the
caret constraint is intentionally loose.

## Components

### 1. `SettingsStore` (MobX)

File: `lib/presentation/settings/store/settings_store.dart`

Observables:
- `String? _aboutInfo` — formatted multi-line string; null until first load.
- `bool _loading` — true while the plugins are resolving.
- `String? _errorMessage` — set if either plugin call throws.

Actions:
- `Future<void> loadAboutInfo()` — if `_aboutInfo` is already non-null, the
  action returns the cached value's wrapped future (idempotent). Otherwise it
  calls `PackageInfo.fromPlatform()` and `DeviceInfoPlugin().deviceInfo`
  concurrently, formats the results into a single string, and stores it in
  `_aboutInfo`. Catches all exceptions and sets `_errorMessage` instead. The
  action is exposed as a method on the store so it can be invoked from the
  `AboutDialog` parent (not from a MobX reaction).

The store is registered as a lazy singleton in
`lib/presentation/di/module/store_module.dart`, alongside the existing stores.

### 2. `SettingsDialog` (StatelessWidget)

File: `lib/presentation/settings/settings_dialog.dart`

Material `AlertDialog` with:
- **Title:** localized `home_tv_settings`.
- **Body:** three `ListTile`s, each `Observer`-wrapped where state is read.
  - **Language** — leading `Icons.language`, title localized
    `home_tv_choose_language`, subtitle = current language name from
    `LanguageStore.getLanguage()`. Tapping pops the dialog and re-opens the
    existing language dialog (see "Reuse" below).
  - **Theme** — leading `Icons.brightness_6`, title "Theme", subtitle =
    localized `settings_tv_theme_dark` or `settings_tv_theme_light` based on
    `ThemeStore.darkMode`. Tapping toggles via
    `ThemeStore.changeBrightnessToDark(!darkMode)` — does not pop the dialog
    so the user can see the subtitle update.
  - **About** — leading `Icons.info_outline`, title localized
    `home_tv_about`, trailing `Icons.chevron_right`. Tapping pops the dialog
    and opens `AboutDialog`.
- **Actions:** single `TextButton` "Close" (`settings_btn_close`) that pops
  the dialog with `Navigator.of(context).pop()`.

The dialog is built via a public `showSettingsDialog(BuildContext)` helper
that wraps `showDialog` for callers in `home.dart`.

### 3. `AboutDialog` (StatelessWidget)

File: `lib/presentation/settings/about_dialog.dart`

Material `AboutDialog`-style layout:
- **Title:** localized `home_tv_about`.
- **Body:**
  - App icon (reuse `AppIconWidget` from `lib/core/widgets/app_icon_widget.dart`).
  - App name (`settings_et_app_name`) and version+build (e.g. "1.0.0+1") on
    one line.
  - Short description (`settings_et_about_description`) as a paragraph.
  - `Observer` showing one of:
    - `settings_tv_loading` while `SettingsStore.loading`.
    - The formatted device-info string from `SettingsStore.aboutInfo`.
    - `settings_tv_error_loading_info` if `SettingsStore.errorMessage` is set.
- **Actions:** `TextButton` "Close" that pops.

`initState` of the calling `showDialog` triggers
`SettingsStore.loadAboutInfo()` exactly once (idempotent guard in the store).

### 4. App-bar entry point

File: `lib/presentation/home/home.dart` (modify only)

In `_buildActions`, insert a new `IconButton(Icons.settings)` between the
existing theme button and logout button. Tapping calls
`showSettingsDialog(context)`. The existing language, theme, and logout
buttons are left in place — this dialog is additive.

### 5. Reuse: existing language dialog

`home.dart`'s `_buildLanguageDialog` is `private` and depends on `_themeStore`
and `_languageStore` instance fields. To reuse it from `SettingsDialog`, the
simplest, lowest-risk refactor is:

- Extract `_buildLanguageDialog()` into a top-level function
  `showLanguageDialog(BuildContext, {required ThemeStore, required LanguageStore})`
  in `home.dart`, leaving the existing private method as a one-line wrapper
  that calls it with the instance fields. `SettingsDialog` then calls the
  top-level function. No behavior change for the existing call site.

This avoids duplicating the dialog body and respects the "improve code you
touch" principle without expanding scope.

## Data Flow

```
HomeScreen IconButton (settings)
  → showSettingsDialog(context)
    → showDialog(builder: (_) => SettingsDialog(...))
      ├─ Language row tap
      │   → pop SettingsDialog
      │   → showLanguageDialog(...)  (existing)
      │       → LanguageStore.changeLanguage(...)
      ├─ Theme row tap
      │   → ThemeStore.changeBrightnessToDark(!darkMode)  (in place)
      │   → Observer rebuilds subtitle
      └─ About row tap
          → pop SettingsDialog
          → showDialog(builder: (_) => AboutDialog(...))
              → SettingsStore.loadAboutInfo()  (once)
              → Observer renders loading / info / error
```

## Error Handling

- `SettingsStore.loadAboutInfo` wraps both plugin calls in a single
  `try/catch`. On failure, `_errorMessage` is set and `_aboutInfo` stays
  null. The `AboutDialog` body shows the localized error string.
- Theme and language actions reuse the existing `ErrorStore`s; no new error
  paths are introduced.
- No new `Flushbar` is added to avoid stacking notifications.

## Testing

Widget tests under `test/presentation/settings/`:

1. `settings_dialog_test.dart` — pumps `SettingsDialog` inside a `MaterialApp`
   with the existing test `getIt` registrations. Asserts:
   - All three rows render.
   - Default subtitle shows the current language and "Light".
   - Tapping the theme row flips `ThemeStore.darkMode` to `true` and the
     subtitle updates without rebuilding the dialog tree.
2. `about_dialog_test.dart` — pumps `AboutDialog` with a fake
   `SettingsStore`. Asserts:
   - Loading text appears first.
   - The formatted info string appears after the store's `loadAboutInfo`
     future resolves.
   - An error state renders the error key.

Both tests reuse the helper patterns from the existing
`test/presentation/home/` and `test/presentation/post/` test files. The
`getIt` test harness from those tests is extended with `SettingsStore` and
`ErrorStore` registrations as needed.
